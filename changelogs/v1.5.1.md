## Overview

Release 1.5.1 improves access control, retrieval quality, multi-turn chat,
document replacement, worker recovery, community indexing, and operational
recovery. Follow-up updates harden dependencies and error handling, replace
mutable optional-ML installations with verified read-only artifacts, add
fail-closed blue-green deployment controls, and bound graph summarisation to
the real model context window.

The release closes several cases where the system could return stale or
out-of-scope content, strengthens document reprocessing without changing
document identity or access grants, and makes community embedding updates
incremental and resumable. It also adds backup verification and isolated
restore tooling so recovery procedures can be tested before they are needed.

## Access Control

### Group permissions now apply to RAG retrieval

Group-based document permissions are now enforced throughout the interactive
retrieval pipeline:

- streaming and non-streaming queries;
- DRIFT retrieval;
- agent retrieval tools;
- structured queries;
- vector and graph search;
- result-cache entries.

Users in a tenant with group enforcement enabled only receive content granted
to their groups. An empty grant set returns no documents rather than falling
back to tenant-wide access. Tenant administrators and explicitly privileged
system contexts retain their intended access.

### Privileged worker sessions

The PostgreSQL row-level security policies for documents and chunks now
correctly recognise privileged maintenance sessions while preserving tenant
and group isolation for regular sessions. This restores cross-tenant recovery,
export, backup, and provisioning work performed by trusted workers.

The change is delivered by Alembic revision `20260729_2100`. The migration
replaces policy definitions only; it does not transform or delete application
data.

## Retrieval and Answer Quality

### Non-ready documents are excluded

Documents that are still processing or have failed no longer contribute stale
chunks to vector or graph retrieval. The filter is applied inside the search
backends, before result limits, so valid results are not displaced by entries
that will later be discarded.

### No-coverage queries can stop before generation

A configurable post-rerank relevance floor can remove results that do not meet
the required relevance level. When no result remains, Amber uses the existing
no-results response and skips the final generation call.

The setting is opt-in through `RERANK_SCORE_FLOOR`; leaving it unset preserves
the previous behaviour. The floor is included in result-cache keys, so changing
it does not require manual cache invalidation.

### Hybrid threshold handling

Hybrid dense and sparse search now accepts and applies an explicit threshold
on its own score scale. Dense cosine thresholds are not reused for fused
results, avoiding a scale mismatch that could remove every hybrid candidate.

### Query rewriting

The multi-turn query rewriter now:

- uses a real execution deadline;
- falls back to the original query on timeout;
- rejects empty or disproportionate rewrites;
- removes model reasoning blocks before search;
- treats an unterminated reasoning block as invalid output.

A cache entry whose stored chunk IDs no longer resolve is now treated as a
cache miss and rebuilt from a live search instead of producing an empty answer.

### Structured API queries

Non-streaming structured queries now return their structured result directly.
Conversation persistence no longer assumes that every response type has a
conversation identifier.

### Better responses when documentation is missing

The default generation prompt can provide a concise refusal followed by
grounded pointers to the closest available topics. The system does not invent
document names when title metadata is unavailable, and refusal detection
recognises the supported English and Italian forms.

## Multi-Turn Chat

Streaming conversations now persist through the same tenant-aware database
session used by the request. This fixes both conversation history writes and
the detection of conversations that previously entered agent mode.

When multi-turn reinjection is enabled, Amber reads the most recent owned
conversation turns and supplies them to retrieval and generation. Follow-up
questions such as "How do I disable it?" can therefore be rewritten against
the preceding topic rather than searched in isolation.

History is bounded by turn count and character budgets. Malformed turns are
ignored individually, refusals are not reused as answer context, and a missing
or inaccessible conversation degrades to a query without history.

Ollama and Ollama Cloud streaming generation now include conversation history
in the message sequence. The feature remains opt-in through
`ENABLE_MULTITURN_HISTORY_REINJECTION`.

## Document Ingestion and Replacement

### Replace in place

Updated content from the same connector item, source URL, or filename now
reuses the existing document record instead of creating a second logical
document. Preserving the document ID also preserves shares and group grants.

Exact content matches remain no-op deduplications. Content changes update the
stored hash, metadata, object path, processing state, chunks, vectors, and graph
content through the normal ingestion pipeline.

### Version-safe object storage

Replacement objects use a content-derived storage path. Uploading a new version
no longer overwrites the bytes of the version it supersedes, which keeps the
previous source available if reprocessing fails.

Superseded objects are retained. Automatic object garbage collection is not
part of this release.

### Cache consistency

Replacing document content invalidates the tenant result cache immediately,
before reprocessing begins. Cached answers cannot continue to resolve old
chunks under the updated document metadata.

### Recovery of queued documents

The recovery sweep now detects documents that reached `INGESTED` but were never
picked up by a worker. Recovery is bounded per sweep and uses a minimum age so
active work owned by another worker is not reclaimed during normal processing
or a rolling restart.

## Graph and Community Indexing

Community embeddings now use a versioned content marker derived from the
summary and embedding configuration. An incremental refresh embeds only new or
changed communities instead of rewriting the full community index.

Progress is acknowledged after each successful vector-store batch, allowing a
retry to resume from the remaining batches. Explicit full resynchronisation
uses a stable run identifier and is resumable as well.

If a summary refresh fails, Amber keeps the previously published summary
available rather than replacing it with a failed result.

Community-summary prompts are now budgeted against the resolved model context
window. Oversized community rosters are reduced deterministically instead of
being sent beyond the provider limit, and retries resume only the failed or
stale work. Token counting reuses a process-local encoding cache so repeated
budget checks do not rebuild tokenizer state.

## Provider Updates

- The default Ollama Cloud model has moved from the retired
  `gemma3:27b` identifier to `gemma4:31b-cloud`.
- Ollama-compatible streaming generation now honours conversation history.
- Proxied cloud models receive a clamped `num_ctx` derived from the same
  resolved budget used by graph summarisation. Only explicitly cloud-tagged
  models use the proxy-specific budget path.
- Provider configuration remains tenant-overridable.

## Security and Dependency Hardening

Observability health responses no longer return raw dependency exception
messages. Detailed failures remain available in server-side logs while public
responses use stable status values.

The backend ASGI stack, `pydantic-settings`, Python lockfile, frontend runtime
dependencies, and Vitest/Vite toolchain have been upgraded to patched versions.
Streaming routes now divide database work into short tenant-scoped phases, so
provider latency does not retain a PostgreSQL checkout for the lifetime of an
SSE response.

The unused Marker parser dependency chain has been removed. Optional OCR,
ranking, sparse retrieval, and embedding packages are now separated from the
core runtime, reducing both the default dependency surface and the risk that a
runtime installer changes production packages in place.

## Operations and Recovery

### Verifiable backups

The Neo4j backup path now produces replayable Cypher output. New verification
tooling checks backup checksums, database archives, object-store archives,
Milvus metadata, and required restore configuration before a backup is
accepted.

An isolated restore command refuses to overwrite an existing Compose project's
data volumes and runs backup verification as a mandatory preflight. The
migration runbook documents backup, restore drill, cutover, validation, and
rollback.

### Safer worker restarts

- Worker recovery no longer reclaims recently updated work.
- Startup no longer clears community locks owned by other live workers.
- Workers receive a five-minute graceful stop window so acknowledged-late tasks
  can finish or return safely to the queue.
- Child-process recycling bounds long-term worker growth between tasks.

### Memory limits

Memory limits remain on stateless or recoverable services where a restart is
safe. Hard limits were removed from Neo4j and Milvus after comparison with
observed peak usage; terminating a stateful datastore during a write would be
more damaging than allowing the host to reclaim memory elsewhere.

### Deployment checks

The production smoke test now probes the frontend through the Nginx endpoint
used by the deployed topology. The quality gate also passes end to end with
pinned Ruff, mypy, and React Hooks lint versions.

### Verified optional-ML runtime

Optional machine-learning packages are delivered as versioned, prevalidated
runtime artifacts rather than updated in place. Promotion checks verify package
versions, model availability, filesystem ownership, free space on the Docker
storage root, and read-only mounts before a candidate can start.

Canary startup no longer writes metadata, creates a development API key, runs
migrations, or repairs runtime dependencies. Artifact-owned model caches are
mounted read-only, and the same provider configuration is supplied to API and
worker candidates.

Worker upgrades use a blue-green handover: each candidate proves readiness on
an isolated queue, existing consumers are drained, and rollback restores the
previous consumers if any gate fails. Memory headroom, queue state, database
isolation, model loading, health checks, and post-cutover smoke tests are all
fail-closed gates.

## Current Status

As of 2026-08-01:

- The code covered by this release is deployed.
- API readiness, frontend smoke checks, and end-to-end RAG queries pass.
- Retrieval returns grounded answers with source citations.
- The document recovery backlog created before this release has been processed
  without removing source objects or persistent volumes.
- Historical failed ingestion records remain quarantined from retrieval and
  are tracked separately for recovery.
- Existing ready community embeddings carry the current version marker and
  incremental refreshes skip unchanged entries.
- Scheduled backup, document synchronisation, and guarded cleanup jobs are
  enabled.
- The H4 optional-ML runtime is active behind verified read-only mounts, and
  workers were promoted one at a time with drain and rollback gates.
- Community-summary budgeting, retry resumption, tokenizer caching, and
  proxied context limits are deployed.
- No datastore migration in this release deletes or rewrites document content.

### Known limitations

- Multi-turn reinjection currently covers the streaming chat path. Non-streaming
  and agent paths are tracked separately.
- Citation relevance values are used internally for ranking but are not yet
  exposed as an interpretable metric in the user interface.
- Very large communities use a deterministic, bounded subset of their roster
  when the complete source material cannot fit the configured model window.
- Additional hardening remains planned for non-interactive evaluation and
  system retrieval contexts; authenticated user-facing query paths carry their
  resolved tenant and group scopes.
